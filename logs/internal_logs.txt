JSON Design Decisions

No Generic get()

A generic API like:

json.get<int>("age")

was intentionally avoided.

Reason:

- Requires generic syntax support in method calls.
- Complicates parser design.
- Complicates type inference.
- Does not match existing builtin naming conventions.

Instead, JSON uses explicit typed methods:

json.getInt("age")
json.getString("name")

This matches existing APIs such as:

toInt()
toString()

---

JSON Error Handling

All JSON failures use:

zen_error("JsonError", ...)

Handled cases:

- Missing keys.
- Wrong value type.
- Invalid JSON syntax.
- Array out-of-bounds access.

This keeps JSON errors consistent with other runtime errors:

- ClipboardError
- MemoryError

---

JSON Memory Model

"JsonObject" and "JsonArray" returned from:

- "getObject()"
- "getArray()"
- "arrayGetObject()"
- "arrayGetArray()"

are views into the parent JSON tree.

They are not deep copies.

Example:

Json child = json.getObject("user")

The parent must remain alive while the child is used.

Calling:

json.free()

while child references are active causes a use-after-free.

This follows the same manual memory contract as:

List.free()

---

Runtime Implementation

JSON runtime:

- Custom recursive-descent parser.
- No external dependencies.
- Self-contained "_zen_json_*" runtime implementation.
- Uses opaque "ZenJson*" backing storage.

---

Builtin Struct Semantics

All builtin structs now follow reference semantics.

Examples:

- "Json"
- "JsonArray"
- "JsonObject"
- "HttpServer"
- "HttpRequest"

Opaque structs are runtime-managed objects represented as pointers.

---

Compiler Improvements

- Added support for opaque builtin struct allocation.
- Fixed reference storage handling for opaque structs.
- Improved builtin method dispatch and validation.

---

Design Notes

The temporary "Map" / "Maap" experiment was discarded.

Reason:

- Runtime dynamic keys conflict with ZEN's static type system.
- APIs like:

map.getList<int>()

would require:

- Generic parsing.
- Nested generic type handling.
- Runtime type metadata.
- More complex compiler semantics.

JSON already provides dynamic data handling, so keeping typed collections and using JSON for dynamic structures gives a cleaner language design.

Map Design Change Note

Map is no longer a data type

The "Map" type has been removed from ZEN's data type system.

Previously:

- "Map" was treated as a dedicated data structure/type.

Now:

- "Map" is implemented as a built-in struct.
- It follows the same model as other built-in structs.
- Map values are opaque runtime-managed objects.

Map Literal Support

Map supports struct-style literals:

{
    name: "Jishith",
    age: 25,
    skills: ["LLVM", "Compiler"]
}

Map literals can be passed directly, returned from functions, stored in lists, and used as arguments.

Dynamic Fields

Unlike normal structs, Map fields are not fixed at compile time.

Fields are free to add:

{
    name: "Alice",
    age: 20,
    country: "India"
}

A Map can contain different keys depending on usage.

Map Methods

Supported operations:

- "setInt(key, value)"
- "getInt(key)"
- "setDouble(key, value)"
- "getDouble(key)"
- "setBool(key, value)"
- "getBool(key)"
- "setString(key, value)"
- "getString(key)"
- "setList(key, value)"
- "getList(key)"
- "setMap(key, value)"
- "getMap(key)"
- "remove(key)"
- "has(key)"
- "free()"

Runtime Model

Map uses an opaque runtime representation internally.

Users interact through methods only; memory layout and storage are managed by the runtime.
